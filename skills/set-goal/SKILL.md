# 定目标 set-goal

## 目标与边界

通过持续对话帮助用户从模糊想法中确认真正要改变的结果、范围、约束和成功信号。定目标是交互收敛，不是首轮就生成一份看似完整的目标文档。

## 交互协议

对话按事实在以下状态间推进，用户否定或补充关键信息时可退回：

1. **探索**：理解当前情境、核心困扰、动机和期待变化。
2. **收敛**：在候选目标中确定主目标，明确对象、范围、取舍和硬约束。
3. **确认**：起草目标理解，请用户修正或明确确认。
4. **交接**：只在确认后产出最小目标卡和下一阶段入口。

每轮只处理最可能改变目标方向的未知项，默认只问一个核心问题；最多同时问三个可一起回答的紧密相关短问题。用户说“不知道”时，可提供少量候选解释、具体场景或取舍帮助比较，但不替用户做价值决定。

## 确认契约

只有以下信息足以支撑下一阶段时才请用户确认：

- 要改变的现状或期望结果。
- 主要对象和关键场景（确实相关时）。
- 主目标、次要诉求与实现手段已分开。
- 范围、非目标、硬约束和可观察成功信号。
- 不再存在会改变方向的关键未知项。

用自然语言起草并明确询问“这是你想推进的目标吗？”。用户确认前，该陈述只是待验证理解，不是最终目标。

## 产出与完成判据

用户确认后，产出只包含必要字段的目标卡：

- 目标与背景/动机。
- 范围与非目标。
- 会影响后续的约束和已确认假设。
- 可观察、可验证的成功标准。
- 不阻塞下一步的未决问题和推荐入口。

用户认可“这就是我要解决的问题”，且下一阶段不需重新猜目标时，本阶段完成。

## 关键约束

- 不把“做一个 App”、“加 AI”或其他方案/交付物直接当成目标。
- 不在首轮换个说法重述用户请求后就称已澄清。
- 不连续抛出问卷，不重复询问已回答内容。
- 不为价值取舍擅自拍板，不填补会改变方向的未知项。
- 用户确认前，不进入需求、设计、计划或实现。

## 停止与交接

关键判断需要证据时转 `find-proof` 后再继续收敛。用户暂停时只记录已确认内容和剩余关键问题。用户确认目标后，按实际需要交给 `find-proof`、`write-brief`、`make-design`、`make-plan` 或直接执行。
