# 关键路径验证

关键路径验证是一份按风险定义的证据契约，用来证明关键行为跨越真实边界后仍然可用。
它不是某一种测试，也不要求所有项目照搬同一套验证层级。

## 何时需要

改动涉及以下任一情况时，应定义关键路径验证：

- 关键用户流程或运维流程；
- 鉴权、支付、迁移或持久化状态；
- 多个组件、进程、服务或信任边界；
- 异步、流式、实时、重试或恢复行为；
- 失败会造成较高的用户、资金、安全或运维影响。

## 契约字段

关键路径验证必须定义：

- `关键路径`：有顺序的行为和可观察结果；
- `风险`：本次验证必须发现的失败；
- `必需层级`：由风险决定、不可省略的最小证据层级；
- `状态准备`：初始状态、测试数据、账号、缓存和重置规则；
- `外部访问`：访问外部资源的显式开关和安全边界；
- `证据`：机器可读产物或可复查输出；
- `清理`：需要释放的进程、会话、设备、连接和数据；
- `结论`：`通过`、`失败`、`部分验证` 或 `阻塞`。

## 状态矩阵与流程契约

状态矩阵回答“某一刻应该怎样”，流程契约回答“用户或操作者一路走下去是否仍然正确”。用稳定
ID 让规格、计划、验证和评审可以互相追踪：

| ID | 用途 | 至少定义 |
|---|---|---|
| `STATE-*` | 会改变结果的状态或组合 | 前置状态、触发事件、可观察结果、恢复/重进结果、事实来源 |
| `FLOW-*` | 跨边界的完整目标 | 起始条件、连续动作、中途检查点、终态、必测扰动、经过的`STATE-*` |
| `HR-*` | 需要独立人判断的抽查 | 风险理由、关联`FLOW-*`、准备方式、最短步骤、预期结果、证据入口 |

只列状态维度不够，要展开会改变结果的组合；有意排除的组合写明降级行为。流程至少覆盖主成功
路径，并按风险覆盖中断、恢复、重试、重复操作、持久化或时序扰动。纯局部、无状态的改动可注明
不适用，不为凑表制造空用例。

## 证据层级

只选择风险需要的层级：

1. `静态`：类型、lint、结构定义、生成物或规则检查。
2. `单元`：隔离的逻辑或组件行为。
3. `契约`：模块、进程、服务或协议之间的边界。
4. `集成`：真实代码路径、真实适配器和受控依赖。
5. `系统`：组装后的运行环境，包括启动、依赖装配、生命周期和用户可见行为。
6. `视觉或人工`：自动化无法完整判断的视觉一致性或人工判断。

低层证据不能自动证明高层行为。代码路径探针可能通过，但系统启动、依赖装配、
持久化、权限或表现层仍可能失败。

点状证据不能替代流程证据。`FLOW-*`的通过必须来自同一次连续执行，包含起始状态、中途检查点和
终态；不能把不同单测、接口调用或局部 UI 操作里的 PASS 拼接起来。测试夹具或直接修改内部状态
可以用于准备数据，但不能冒充真实入口。

人工抽查与自动/流程验证分别记录。AI 可以推荐`HR-*`并整理证据，但未得到人的明确反馈时只能标
`未抽查`；人的抽查也不能替代未执行的必需流程。

## 阶段职责

- `write-spec` 定义关键路径、风险、必需层级、验收标准、`STATE-*`、`FLOW-*`和人审状态；AI 不自行授予确认。
- `make-plan` 把必需层级展开成命令、前置条件、证据产物和清理动作，并安排`HR-*`候选。
- `build-it` 补齐契约需要的最小可复用测试、探针、日志或可观察点。
- `prove-it` 分别执行点状检查与连续流程、整理人审包、保存证据并给出结论。
- `review-it` 检查状态、流程和人审证据是否可追踪，未确认项不得被描述成已通过。
