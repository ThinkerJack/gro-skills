# 验证它 prove-it

用本轮实际运行的、可复查的证据，判定改动是`通过`、`失败`、`部分验证`还是`阻塞`。

## 四态

| 结论 | 含义 |
|---|---|
| `通过` | 所有必需层级都执行了，且都满足验收标准 |
| `失败` | 某个必需层级执行了，发现错误行为 |
| `部分验证` | 已执行的都过了，但仍有必需层级没执行 |
| `阻塞` | 环境、权限或外部依赖不可用，必需验证跑不了 |

**只有第一种才叫通过。** 后三种在总结时保持原样——`部分验证`不写成「基本通过」，`阻塞`不写成「已完成」。

## 证据规矩

- 声称什么，就先跑证明它的那条命令，并读完整输出
- 没有本轮新鲜证据时，说「还没验证」，不说「应该没问题」
- 只跑了部分检查，结论就只覆盖那部分
- 失败先分类：本次改动引入的、既有的、还是环境问题。前者修完必须复验
- 证据和日志里不出现密钥、令牌、cookie、个人数据、生产数据原文

## 流程证据与人审

- 规格有`FLOW-*`时，从真实入口连续执行到终态，记录经过的`STATE-*`、中途检查点和终态证据
- 不把多个点状 PASS 拼成流程 PASS；低层检查通过不自动证明组装后的行为
- 按计划整理`HR-*`人审包；AI 可以推荐和取证，但没有人的明确反馈只能标`未抽查`
- 人审结论与四态验证结论分开记录：人工抽查不能替代未执行的必需验证，自动验证也不能冒充人审

## 交付

结论放在证据明细前，先给一屏内的验收卡：

```
结论        通过 / 失败 / 部分验证 / 阻塞
证明了什么  一句话
没证明什么  一句话；没有就写「无」
最大风险    一句话
建议动作    交付 / 修复 / 补验证 / 解除阻塞
```

证据明细再列：实际检查与结果 · 证据产物路径 · 每个`STATE-*`/`FLOW-*`的覆盖结论 · `HR-*`
人审状态 · 未执行的层级和残余风险。
