# 修问题 fix-bug

先解释失败，再修。

## 顺序

1. **留证**——修改前保存原失败的可复查证据（完整报错、复现步骤、相关输出）
2. **复现**——能稳定触发吗？步骤是什么？不能复现就先说明缺什么证据，而不是凭猜改代码
3. **定位根因**——用可证伪的假设组织排查；跨组件时在每个边界记录进出的数据，看清在哪一层断的
4. **最小修复**——只覆盖根因和必要的回归保护
5. **复验**——重跑原失败路径，加上与改动风险匹配的回归检查

## 两条硬规矩

**根因确认之前，只做诊断性改动。** 加日志、埋探针、插临时断言、收窄复现范围都该做——很多根因不插桩定位不到。**修复性**改动才要等根因确认：改了三处然后好了，等于不知道哪处起了作用。

**同一时间只试一个假设。** 不成立就退回重新分析，不在前一个修改上继续叠。连续三次被推翻后停止试错，回头检查复现路径是否稳定、观测点是否够、环境假设是否成立、边界是否画错——最常见的原因是证据不足，其次才是架构问题。

## 完成的标准

原失败被解释清楚、修复对得上根因、原路径复验通过。三者缺一就还没完。

契约测试、断言和验收标准是用来发现问题的，不是用来让它通过的。

## 人区 · 故障说明卡

修复完成时先给一屏内的因果说明：

```
现象        人能观察到的失败
根因        一条因果链，不写排查流水账
修复        改变了哪个关键行为
为什么有效  修复如何直接切断根因
残余风险    还可能在哪些条件下失败
```

完整报错、探针、被推翻的假设和复验输出留在后面的证据区。

## 交接

复现不了：说清需要什么证据后停下。失败暴露了需求或设计缺口：回到 `make-sketch` 或 `write-spec`。修复完成：转 `prove-it` 做完整验收。
