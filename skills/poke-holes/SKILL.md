# 挑毛病 poke-holes

## 目标与边界

对用户指定的想法、需求、方案、计划或技术判断做对抗性审视，暴露最可能改变决定的矛盾、隐含假设、失败模式和证据缺口。目标不是一次性给出判决，而是通过多轮对话把真正的分歧、误读和适用边界聊清楚。

挑毛病不等于把目标拔高、补充另一个观察尺度或用更复杂的表达替换原话。更高层视角可以提出，但必须标为“补充框架”，不能伪装成原主张的错误。

## 工作流

### 1. 先抓主张，不急着反驳

提取最影响当前决定的 1—3 个核心主张，先准确复述其对象、语境和适用范围。用户已经限定团队、阶段、理想条件或目标层级时，在该边界内审视，不用边缘反例击倒一个本来就有条件的判断。

### 2. 区分挑战类型

发出批评前，判断它属于哪一类：

- **真实缺陷**：内部矛盾、关键假设不成立或存在明确失败后果。
- **证据缺口**：主张可能成立，但当前证据不足；说明需要什么证据，不下确定结论。
- **上下文未知**：结论取决于团队、阶段或约束；明确假设，必要时只问一个最改变方向的问题。
- **表述过强**：方向可能正确，但绝对化措辞会引出不必要反例。
- **补充视角**：从更高或不同维度重构问题；说明它是扩展，不把它说成纠错。

### 3. 给出可讨论的挑战

每个关键挑战至少包含：

1. 被挑战的具体主张，以及为什么值得挑战。
2. 它成立所依赖的隐含假设。
3. 如果假设错误，一个可观察的实际失败后果。
4. 当前判断的不确定性或缺失事实。
5. 一个保留用户原意、可以直接比较的替代表述或处理方式。

默认只展开最关键的少数问题，不用风险清单淹没主线。替代表述应当与原文一样易懂或更易懂；不能为了显得严谨，堆叠抽象概念、条件和术语。

### 4. 把第一轮当成待验证判断

第一轮审视不是最终结论。提出最关键的分歧后，邀请用户回应其真实背景或价值取舍，不立刻把所有观点改写成完整方案。

用户澄清后逐项明确：

- **保留**：原挑战仍成立，并说明剩余分歧。
- **修正**：方向成立，但需要根据新上下文缩小或改写。
- **撤回**：承认此前误读、过度推断或把补充视角当成了纠错。
- **升级**：双方认可新视角确实改变目标或范围，再交回相应阶段继续处理。

收敛时总结已经达成的共识、仍有分歧的判断和暂不处理的问题，避免表面同意后丢失真正的差异。

### 5. 选择合适的反馈载体

默认在对话中反馈。若用户授权直接评论可编辑文档，优先保留原文并用文档原生评论、批注或 Markdown callout 标出问题；在观点尚未聊清前，不擅自重写作者结论。用户确认共识并要求修改后，再交给适合的写作或执行阶段落地。

## 产出与完成判据

- 核心主张被准确理解，没有把适用范围内的判断偷换成无限命题。
- 真实缺陷、证据缺口、上下文未知和补充视角被明确区分。
- 至少一个关键问题给出了可观察的失败后果，而不是泛泛提醒风险。
- 用户澄清后，挑战被明确保留、修正或撤回，不把误读继续包装成分歧。
- 最终建议能落到继续、修改、缩小范围、暂停或先取证，并保持表达清楚。

关键风险已经被接受、缓解、改写或明确需要证据，并且下一阶段不需要重新猜双方的真实分歧，才算完成。

## 关键约束

- 不为显得审慎而编造低相关或无法行动的风险清单。
- 不把“我还能想到更高层目标”当作“你的目标错了”。
- 不为了覆盖所有反例，把一句清楚、有记忆点的话改成难以理解的条件集合；必要边界可以单独说明。
- 不默认所有问题都需要复杂治理。用户认为某个常识无需展开时，除非存在高代价反例，否则尊重其表达取舍。
- 不把事实缺口包装成已确定结论；需要证据时转 `find-proof`。
- 不擅自替用户决定价值取舍。

## 停止与交接

高风险假设已被接受、缓解、改写或明确需要证据时停止。需要修改原始产物时，根据用户授权交回原阶段，或转 `find-proof`、`write-brief`、`set-goal`、`make-design` 或 `build-it`。
