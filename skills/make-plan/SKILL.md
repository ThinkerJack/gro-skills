# 拆计划 make-plan

计划的核心职能是**把测试和验收绑进「完成」的定义**：做完一步不等于代码写完，而是代码写完加验证通过。

计划落库，供 `build-it` 对照判断是否偏移。用户明确要口头计划、任务已缩成单步、或当前环境不能写文件时例外。

## 人区 · 执行路线

计划最前放一屏内的执行思路，让人先判断路线对不对：

```
结果路径    3—7 步说清能力如何逐步变得可用
关键顺序    哪些依赖决定了排序
交付节点    中途停在哪里仍是完整状态
需要确认    人、真设备、外部系统或额外授权
最大风险    最可能让计划失效的一件事
```

这里只写路径和取舍；文件、命令和每步证据放在后面的执行区。

涉及产品行为、跨边界流程或高风险状态时，先确认规格人审状态为`已确认`。纯工程任务可标
`不适用`并说明不改变产品行为。行为级未决项退回`write-spec`，不在计划里临场补需求。

## 每个任务写四件事

```
改哪里    文件或模块范围
完成什么  这一步结束时什么可用
怎么验证  具体命令或操作，不是「测试通过」这种空话
预期看到  命令的预期输出或可观察结果
```

**没有验证方式的任务不算拆完。** 如果一步无法验证，它要么该合进相邻步骤，要么缺了可观察点——回到 `write-spec` 补。

## 分开三类验证

- **点状检查**：每个任务完成后证明局部契约成立，引用对应验收项或`STATE-*`。
- **流程验收**：组装完成后，从真实入口连续执行每条`FLOW-*`到终态；不能把不同测试里的局部
  PASS 拼成一次流程 PASS。
- **人工抽查**：AI 按风险提出少量`HR-*`候选，写明关联`FLOW-*`、准备状态、最短步骤、预期结果
  和必须由人判断的细节。未经人的明确反馈只能标`未抽查`。

计划保留`FLOW-* → 实现任务 → 自动检查 → 运行证据 → HR-*`追踪。

## 排序

按依赖排，不按文件排。能独立交付的边界要标出来，让中途停下也是一个完整状态。

标出需要人工确认的位置：外部系统、真设备、付费资源、生产环境——**这些不因为写进计划就获得授权**。

## 硬线

- 关键步骤不留 `TBD`、`TODO`、「按需」、「类似」、「等等」
- 只写下游必须遵守的边界、产物、依赖和证据，实现细节留给执行者
- 计划无法拆解时，原因通常在上游：回到 `write-spec`、`design-it` 或 `sketch-it`

## 按需资源

规格定义了关键路径时，读取`prove-it` skill 的`references/critical-path-verification.md`，把必需
证据层级展开成前置条件、命令、预期证据、清理动作和失败退出条件。

## 交接

执行者能直接照计划进入 `build-it`、不必重新设计整体方案时停止。
