# 做设计 design-it

确定改动怎么组织：模块边界、数据怎么流、依赖谁、用哪套技术。不定义产品需求，也不拆执行步骤。

## 人区 · 选型卡

一屏之内，只放需要人拍板的：

```
要解决什么  一句话：什么约束逼出了这次设计
选了什么    推荐方案，一句话说清它怎么组织
否掉了什么  2—3 个认真比较过的替代，各一句：不选的真实原因
赌在哪      这个方案依赖的关键假设；假设不成立会怎样
不可逆的    以后改起来代价大的决定；没有就写「无」
最大风险    一件事
```

**否掉的选项必须是真比较过的。** 凑数的陪跑选项比不列更糟——它让人以为已经比过了。

**人区超过一屏，就是这次要定的东西太多了**——拆成几个可以分别拍板的决定，不要把一屏压成小字。

## AI 区 · 实现契约

选型卡之后再展开：

- **边界**：动到哪些模块、进程或服务，各自负责什么，谁不该知道谁
- **流转**：与本次改动相关的数据流、状态流或调用流；跨边界的地方标出来
- **接口**：关键函数签名、数据结构、事件、不变量——下游不得靠猜的那些
- **验证策略**：这个设计怎么证明成立，哪些风险要靠运行时证据

## 选型要有依据

性能、成本、生态、团队熟悉度这类比较，**说清数字或事实从哪来**：实测、官方文档、还是印象。印象就标成印象。缺关键事实时转 `find-proof`，不要用听起来合理的判断填进选型理由。

与仓库现状冲突时当场说——现有架构、既定约定、已有依赖，都比一个更漂亮的新方案更有分量。

## 什么时候不做设计

- 边界清楚的单点改动：直接实现
- 只有一个合理方案、且它显而易见：把它写进 `write-spec` 的关键取舍就够了
- 方向本身还没定：先 `sketch-it`

## 交接

设计认可后 → `write-spec` 固化成可验收的规格；范围明确的重任务可直接 `make-plan`。

要对抗性审视这个方案 → `sharpen-it`。关键事实不足 → `find-proof`。方向被推翻 → 回 `sketch-it`。
