# 做评审 review-it

对着 diff 找会挡住交付的问题，按严重度排序。

## 三个维度

**规格覆盖** 该做的做了吗、有没有超出范围的改动、有没有没打招呼的偏移

**证据** `prove-it` 的结论覆盖了主要风险吗、哪些还没验证

**缺陷** 具体到文件和行为，说清影响和建议处理

**人审** 规格是否真的经过确认、`HR-*`是否有人的明确结论、AI 的推断有没有冒充产品决定

先给评审决策卡，紧接着放 findings。改动复述和总体评价放在后面，或者干脆不写。

```
建议      可交付 / 继续修 / 回设计 / 需人工决定
问题数    阻塞 N · 建议 N · 观察 N
主因      为什么得到这个结论
最大空白  最重要的未验证风险
```

## 全报，再分层

**凡是有代码、规格或证据支撑的问题都报出来，不要按重要性预先自我过滤。** 按下面三层标注，让人自己决定看哪层：

```
阻塞      不改不能交付
建议      该改，但不挡这次交付
观察      风格、偏好、可做可不做
```

按严重度排序，阻塞在最前。发现的问题少并不说明质量高，可能只是报得少——这一层的价值来自召回率，过滤是人的事。

没有新鲜验证证据时，结论不能是「可交付」，先回 `prove-it`。

评审证据时分别检查：`STATE-*`是否覆盖会改变结果的组合；`FLOW-*`是否从真实入口连续执行到
终态；`HR-*`未得到人的明确反馈时是否仍标`未抽查`。

## 对象不是 diff 时

`review-it` 看的是**已完成的改动**。如果要评的是还没实现的方案、设计或需求，那是观点碰撞不是缺陷检查——转 `sharpen-it`。

## 交接产物

给合并者或下一个执行者：评审决策卡、完整 findings、`STATE-*`/`FLOW-*`覆盖摘要、`HR-*`人审
状态和剩余风险。摘要控制在一屏。

发现实现缺陷转 `fix-bug` 或 `build-it`；发现需求或设计缺口回到 `sketch-it`、`design-it` 或 `write-spec`。
