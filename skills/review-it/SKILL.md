# 做评审 review-it

## 目标与边界

在交付前评审已完成改动，优先暴露会导致不能合并、不能交接或需要继续修复的问题。本 skill 不评审未实现方案，也不执行 commit、push 或 PR 操作。

## 输入与前提

- 已完成改动的 diff。
- 需求、规格、计划或等价验收基线。
- `prove-it` 的新鲜验证证据及未覆盖风险。

## 产出与完成判据

- 按严重度排序的 findings，每条指向具体文件/行为、影响和建议处理。
- 需求与规格覆盖结论，包括遗漏、超范围或未经确认偏移。
- 验证证据是否覆盖主要风险，以及仍未验证的内容。
- 可交给合并者或下一个执行者的 handoff：改动目的、验证摘要、剩余风险和建议决策。

交付方能根据 findings 和证据判断“可交付 / 继续修复 / 回到设计 / 需要人工决策”时，评审完成。

## 关键约束

- findings 优先；不用改动复述或泛泛好评淹没风险。
- 没有新鲜验证证据时，不给出“可交付”结论，先回到 `prove-it`。
- 不将方案偏好包装成已实现缺陷；只报告有规格、代码或证据基础的问题。

## 停止与交接

发现实现缺陷时回到 `fix-bug` 或 `build-it`；发现需求/设计缺口时回到 `write-brief` 或 `make-design`；评审通过且用户明确要求提交时，再交给 `commit-it`。
