# 做评审 review-it

对着 diff 找会挡住交付的问题，按严重度排序。

## 三个维度

**规格覆盖** 该做的做了吗、有没有超出范围的改动、有没有没打招呼的偏移

**证据** `prove-it` 的结论覆盖了主要风险吗、哪些还没验证

**缺陷** 具体到文件和行为，说清影响和建议处理

findings 放最前面。改动复述和总体评价放在后面，或者干脆不写。

## 全报，再分层

**看到的都报出来，不要预先自我过滤。** 按下面三层标注，让人自己决定看哪层：

```
阻塞      不改不能交付
建议      该改，但不挡这次交付
观察      风格、偏好、可做可不做
```

按严重度排序，阻塞在最前。发现的问题少并不说明质量高，可能只是报得少——这一层的价值来自召回率，过滤是人的事。

没有新鲜验证证据时，结论不能是「可交付」，先回 `prove-it`。

## 对象不是 diff 时

`review-it` 看的是**已完成的改动**。如果要评的是还没实现的方案、设计或需求，那是观点碰撞不是缺陷检查——转 `sharpen-it`。

## 交接产物

给合并者或下一个执行者：改动目的、验证摘要、剩余风险、建议决策（可交付 / 继续修 / 回设计 / 需人工决定）。

发现实现缺陷转 `fix-bug` 或 `build-it`；发现需求或设计缺口回到 `make-sketch` 或 `write-spec`。
