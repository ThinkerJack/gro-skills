# 写规格 write-spec

规格的首要职能是**把散落在多处的信息固化成一个真源**：调研结论、设计稿、接口文档、现有代码、用户口述的约束。做完之后，实现者不必回头重开那些原始资料，几个月后也能回答「这个决定当时基于什么」。

需要与用户对齐时调用 `clarify`；缺关键事实时转 `find-proof`。产出格式与示例见 [SPEC-FORMAT.md](./SPEC-FORMAT.md)。

## 固化信息源的四条纪律

1. **每条关键事实都记来源**——约束、数字、接口形状、业务规则，标明它从哪来：文档 URL、代码路径加行号、调研报告、还是用户某句话。**没有来源的判断标为「推断」**，不混进事实里
2. **冲突当场裁决，并记下被否掉的那个**——写清采信哪个、为什么它更权威、否掉的是什么，而不是挑一个顺手的写进去
3. **标时效**——每组关键事实标注什么时候取的、什么条件下会失效、失效了重新查哪里
4. **与仓库现状交叉验证**——用户口述的「现在是这样的」经常和代码不一致，**发现不一致当场停下来问**，不要默默按其中一个写

## 什么够格进规格

同时满足才写进去：

- **下游会用到**——不影响实现或验收的背景资料留在原文档里
- **不进就得猜**——实现者能从代码直接读到的，给个路径就够，不要抄一遍
- **改起来有代价**——随手可改的细节不值得固化

## 产出结构：人区和 AI 区分开

**人区在前，一屏之内**，只放需要人拍板的：目标、范围、非目标、关键取舍、验收标准。

**AI 区在后**，放实现契约：改动面、字段名、函数签名、路由、事件、文案、常量、状态、接口形状、Given/When/Then 测试契约。

平铺混排会让人在三千字里捞那十行，规格就 review 不动了。

## 硬线

- **人区超过一屏，就是范围该拆了**——拆成多份可独立验收的规格，不要把一屏压缩成小字
- 关键位置不留 `TBD`、`TODO`、「按需」、「类似」、「等等」
- 未决问题会改变行为、接口或验收时，规格不标为可执行

## 按需资源

改动涉及关键用户流程、鉴权、支付、迁移、持久化、多信任边界或高影响失败时，读取 `../prove-it/references/critical-path-verification.md`，在规格中定义关键路径、必需证据层级、状态准备、外部访问边界、清理责任和验收标准。

## 交接

规格可自包含交给 `make-plan` 时停止。方向仍有争议回到 `make-sketch`；关键事实不足转 `find-proof`。
