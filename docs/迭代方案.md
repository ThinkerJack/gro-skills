# gro-skills 迭代方案

> 2026-07-28。基于 [`使用诊断.md`](./使用诊断.md) 的四条根因。
> 触发点：Opus 5 / GPT-5.6 发布。约束：无 eval 基础设施，无固定迭代节奏。

## 一、目标

迭代后应能在日常使用中直接感知，都不依赖 eval：

1. **回到决策环里。** 关键节点由你敲出来，而不是流程自动跑完你在环外看。
2. **第一个控制点一分钟内能拍板。** 面对多信息源需求，看到的第一份东西是十几个 bullet，不是三千字。
3. **小改动不被拖进流程。** 说"帮我改个字段"时，没有 skill 跳出来要求先确认目标。
4. **三个月后能回答「这个决定基于什么信息、什么时候的」。** 打开 spec 就有。
5. **文档能给人读**——包括同事。自述：「所有文档的可读性都是非常重要的」。

**不追求**：跨 session 交接、团队协作规范、流程完整性、覆盖所有工程阶段。

## 二、第一原则：不删，先改触发方式 + 精简

诊断推翻了"这些 skill 没用"的假设——7 月 944 次调用，13 个全在跑。现有证据只能证明**作者对它们无感**，而无感 ≠ 无用。

| 动作 | 风险 | 可逆性 |
|---|---|---|
| 改触发方式 | 低——直接治核心病，不丢失任何现有能力 | 完全可逆 |
| 精简内容 | 低——删错了模型退回默认行为，Opus 5 的默认已经很强 | 可逆 |
| 删除 skill | **高**——可能删掉正在默默兜底的东西，且不会察觉 | 需要重建 |

**所以本轮只做前两件。删除留给下一轮，用第七节的自然实验取证。**

精简还有一层直接收益：7 月 944 次加载，每 1 KB 冗余都在被反复付费，这是「慢」的来源之一。

## 三、精简到什么程度——判据

> **这段文字是在告诉模型「接下来干什么」，还是在反制一个它默认会犯的错？**

- 前者 → 一行，甚至只写调用关系
- 后者 → 展开到那个错误的具体形状

社区参照：`grill-me` 147 B（编排壳）、`grilling` 843 B（纪律）、`verification-before-completion` 3.6 KB（全是 rationalization table，不可删）。

**唯一保留的测试手段是 no-op 测试**，不需要基础设施：逐句问「这句话相对模型默认行为改变了什么」，没有就删整句，不要修剪用词。

**约 50 条禁令的处理**（两个独立来源证实其有害，见诊断 §三.4）：

- 能正向表述的改正向——说目标行为，让被禁的那个不被说出口
- **不写"除非…"豁免**——实测会让有效指令退化成噪声
- 需要条件分支的，挂在**可观测谓词**上（"如果 spec 存在就引用它"），而非"规则 + 例外"
- 只有无法正向表述的硬护栏保留禁令形态（权限类）

## 四、架构

```
控制点层   user-invoked，敲了才出现，零 context load
  /sketch     十几个 bullet：问题、动哪些模块、2-3 方案+推荐、非目标   【新增】
  /spec       信息源固化 ← 唯一允许写厚                          【重写＋合并】
  /plan       执行序、依赖、DoD 绑定测试验收                       【瘦身】

纪律层     model-invoked，保持自动，大幅精简
  访谈纪律    从 set-goal 抽出，对标 grilling 843 B              【新拆】
  find-proof  取证，输出对接 spec 的来源清单
  prove-it    保留四态结论 + 两个 reference，其余精简
  build-it    执行入口，精简后观察
  fix-bug     精简后观察
  review-it   精简；与内置 /code-review 的关系待定

权限层     commit-it —— 不动，权限门槛不适用极简

显式层     poke-holes、save-lesson —— 改 user-invoked
思考层     research —— 不动（Claude Code 侧主力）
```

### 平台分工进设计

诊断显示两平台用途不同，不要假装一套服务两边：

| 平台 | 性质 | 成员 |
|---|---|---|
| Codex | 执行 | 三个控制点 + 纪律层 + commit-it |
| Claude Code | 思考 | research、poke-holes |

### 分发机制：生成式，不是软链

现存四种接入方式并行（软链 3 个仓库、生成式 3 个、独立自有 4 个、未接入若干），需要统一。选型结论是**生成式**——采用 `vlog-app/tool/sync_gro_skills.dart` 已验证的两层模式：

```
.agents/skills/<name>/
├── SKILL.md                    10 行薄壳：读 common → 读 project → 冲突时以就近 AGENTS.md 为准
└── references/
    ├── common.md               gro-skills 原文（生成，带 blob 追溯）
    └── template-<x>.md         本仓经验（手写，永不覆盖）
```

| | 软链 | 生成式 |
|---|---|---|
| **同事 clone 即用** | ✗ 绝对路径，到手是死链 | ✓ 真实文件，可进 git |
| **项目特定层** | ✗ 无处安放 | ✓ `template-*.md` |
| 更新方式 | `git pull` 自动 | 重跑同步（blob 可检测过期） |
| 版本可追溯 | ✗ | ✓ manifest 记录 sourceBlob |

**多人协作是决定性因素**：软链存的是 `/Users/wuchao/...`，同事拿到就断；生成式产出真实文件，clone 即用，同事甚至不需要知道 gro-skills 的存在。

代价是更新不自动，但 `--check` 能一条命令查出过期项——比软链的静默跟随更可控。前提是**把 check 挂进 pre-commit 或 CI**：vlog-app 的 mirror 已两周没同步（`poke-holes` 停在 30 行、上游 80 行），`--check` 本可发现，但没人主动跑。

配套的 mirror / adapter 二分（哪些整目录覆盖、哪些保留项目薄壳）见[实施计划 1.1](./实施计划.md#11-定-mirror--adapter-划分)。

## 五、逐个处置

| skill | 触发 | 内容 | 依据 |
|---|---|---|---|
| **`/sketch`** | 新增 user | 新写，极简 | 直接治「review 不动」与「慢」 |
| **`/spec`** | 改 user | **重写做厚**，并入 write-brief + make-design | 已确认为核心差异化 |
| **`/plan`** | 改 user | 瘦身：只留执行序 + 依赖 + **DoD 绑定测试验收** | 自述真实职能就是后者一句话 |
| 访谈纪律 | 新增 model | 从 set-goal 抽出，对标 grilling | set-goal 里唯一真被用到的部分 |
| `find-proof` | 保持 model | 精简，输出格式对齐 spec 来源清单 | 136 次，重新定位为 spec 上游 |
| `prove-it` | 保持 model | 保留四态 + 两 reference，其余精简 | 140 次；四态是模型不会自发做的 |
| `build-it` | 保持 model | **大幅精简**后观察 | 176 次最高，但内容主体是模型默认行为 |
| `fix-bug` | 保持 model | 精简后观察 | 66 次 vs 自评「没用过」，证据冲突 |
| `review-it` | 保持 model | 精简 | 45 次；与内置 `/code-review` 关系待定 |
| `commit-it` | 不动 | 不动 | 权限门槛 |
| `poke-holes` | **改 user** | 保留内容，考虑改名 | 主动敲的两个之一；名字与 prove-it 混淆 |
| `save-lesson` | 改 user | **新增用途：记录 skill 自身摩擦** | 迭代节奏的载体 |
| `research` | 不动 | 不动 | Claude Code 侧主力 |
| `set-goal` | 拆分 | 访谈纪律抽出，其余并入 `/sketch` | 30 次但作者印象稀薄 |
| `write-brief` | → deprecated | — | **唯一证据充分的**：9 次（最低）+ 自评「基本没用到」 |

结果：**手动 3 + 自动 6 + 显式 2 + 权限 1 + 思考 1 = 13 → 保留 12，降级 1。**

数量几乎没变，但你会主动敲的从 2 个变成 5 个。

## 六、`/spec` 设计要点

唯一需要认真设计的一个。对标 `domain-modeling` 的结构（SKILL.md 讲纪律，格式单独成文件）。

**厚在纪律**（SKILL.md）——模型不会自发做的：

- **冲突裁决**：多个信息源打架时哪个权威、被否决的怎么记
- **时效判定**：这批信息什么时候的、何时失效、哪些需要重新取证
- **准入门槛**：什么够格固化、什么是噪音（参照 ADR 三条门槛的写法）
- **交叉验证**：口述与仓库现状不一致时当场叫停

**厚在格式**（`SPEC-FORMAT.md` 单独文件）：来源清单、冲突裁决、时效标记的骨架。

**绝不厚在**：「产出应包含目标、范围、非目标、关键决定…」——这是现在 write-spec 的主体，也是 review 不动的原因。

**两条硬线**：

- 人区一屏内，超了就拆成多份可独立验收的 spec（现有 write-spec 有这句但无触发条件）
- **人区 / AI 区物理分开**：人只 review 目标、范围、非目标、关键取舍、验收；字段名、签名、接口契约属于 AI 区。两者平铺混排正是「review 不动」的直接原因

## 七、自然实验——不需要 eval 的删除测试

改触发方式本身就是一次免费实验：

- `poke-holes`、`save-lesson` 改手动后，**你还会不会敲**？会 → 有价值；不敲且工作没变差 → 下一轮可降级
- `build-it`、`fix-bug` 精简后，**有没有变差**？没有 → 说明被删的确实是 no-op，下一轮可以继续削

**观察窗口两周，判据是你的实际行为，不是回忆。** 结果记进 `save-lesson`。

这是"删除测试"在无 eval 条件下的可行版本：用触发方式的改变替代 A/B，用你敲不敲替代打分。

## 八、不做成 skill 的三件事

不是所有需求都该做成 skill：

| 痛点 | 处置 |
|---|---|
| 让 AI 用最新 API、必要时联网 | 写进项目 `AGENTS.md`——这是无条件默认行为，不需要触发判定。Context7 与 research 都已配好 |
| 多 session / worktree | Claude Code 原生支持；Codex 侧参照 superpowers-lite——固定 `.worktrees/` 位置，作为执行环节的 setup step，不单列 skill |
| AI 输出太长 | 两条腿：`/spec` 的篇幅硬线；试 `CONTEXT.md` 共享语言（见 `docs/references/mattpocock-skills/`），把「课程 section 里的 lesson 被给了文件系统位置」压成「materialization cascade」 |

## 九、执行顺序

详见 [`实施计划.md`](./实施计划.md)。五个阶段：

```
阶段0 止血（接入缺陷、死链清理）        30 分钟，无依赖
阶段1 统一同步机制（移植工具、迁移）     半天，必须先于所有内容改动
阶段2 改触发方式（只动 frontmatter）    1 小时，自然实验起点
阶段3 内容重构（/sketch、/spec、no-op） 工作量主体
阶段4 观察收敛                        阶段2 起两周后
```

**唯一的硬顺序约束是阶段 1 先于阶段 2**：adapter 的 frontmatter 在项目薄壳里，同步机制不统一就要手改 18 处。

## 十、迭代节奏

不设定期 review——个人开发者不会执行。改为事件驱动：

**`save-lesson` 新增用途**：记录 skill 自身的摩擦——AI 漏了什么、你手动纠正了什么、哪个 skill 误触发或漏触发、第七节的观察结果。**攒够 5 笔改一次。**

这些笔记将来就是 eval 的现成用例，且是真实失败而非想象场景——正是 superpowers 与 Anthropic 官方共同强调的顺序：**先观察到失败，再写指令**。

## 十一、待定

- 三个控制点的正式命名（是否延续现有中英双名风格）
- `/sketch` 与 `/spec` 之间是否允许跳过
- `poke-holes` 是否改名（现状会与 `prove-it` 混淆）
- `review-it` 与内置 `/code-review` 的分工
- 这三份文档是否加进 `docs/.gitignore` 白名单以进入版本控制
