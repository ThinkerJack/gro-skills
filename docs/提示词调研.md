# 2026-07 提示词技巧调研：对 gro-skills 的影响

> 2026-07-28。为评估两份本地资料（[思考脚手架](./references/source-materials/knowledge/notes/用AI帮我想清楚-思考脚手架.md)、[反谄媚实践](./references/source-materials/knowledge/notes/LLM%20sycophancy%20原理与反谄媚提示词实践.md)）能否融入 skill 而做。
> 本文只陈述调研发现与影响判断，不含改动方案。

## 摘要

**最重要的一条**：Anthropic 为 Opus 5 单独出了 prompting 指南，其中多处要求**删除指令**而不是添加——尤其是显式验证指令。这直接冲击我们刚完成的三处改动（`prove-it` 的存在形态、`build-it auto` 的内联验证、`review-it` 的报告范围）。

三条印证、三条冲击、一条空白：

| | 内容 |
|---|---|
| ✅ 印证 | 正向表述优于禁令 · 删指令优于加指令 · 写入文件需显式长度校准 |
| ⚠️ 冲击 | 显式验证指令会导致过度验证 · review 说「只报重要的」会让它少报 · Codex 上「汇报状态」类指令会导致提前停止 |
| ⬜ 空白 | 反谄媚方向 2026-04 之后无新证据，本地笔记仍是最新 |

## 一、Anthropic：Opus 5 要你删掉什么

### 1. 显式验证指令 —— 最需要注意的一条

> 如果你的 prompt 里有显式验证指令（"为任何非平凡任务加一个最终验证步骤"、"用 subagent 验证"），**删掉它们**：这类指令在 Claude Opus 5 上会导致过度验证，删除后减少 token 浪费且无质量损失。**同样适用于额外增加验证步骤的遗留 harness 脚手架。**

通用指南里说得更直接：

> 迁移到 Claude Opus 5 时，**删除这些指令，而不是重写它们**。

### 2. Review 不要说「只报重要的」

> 如果你的 review prompt 说「只报告高严重度问题」或「保守一点」，模型可能字面遵守并**少报**；应该让它**全部报出来，再用单独一遍过滤**。

### 3. 自我纠正也别催

> 避免指示它重新检查那些它本来就会做的事（"再检查一遍答案"、"回答前再验证"）；这类指令会与模型自身行为叠加，增加成本而不改善结果。

### 4. 写入磁盘的文件更长了

> Claude Opus 5 写到磁盘的文件（报告、Markdown 文档、总结）往往比之前的模型更长。

官方给的校准文本：

```
Match the length of written documents to what the task needs: cover the substance,
but do not pad with filler sections, redundant summaries, or boilerplate.
```

### 5. 正向表述优于禁令（官方口径）

> **告诉 Claude 做什么，而不是不做什么**
> 不要：「回答里不要用 markdown」
> 改为：「你的回答应由流畅的散文段落组成」

以及：

> 你想要的沟通风格的**正面示例**，通常比「不要做什么」的指令更有效。

### 6. 激进措辞现在会反噬

> 以前你可能写「CRITICAL: You MUST use this tool when...」，现在用正常措辞「Use this tool when...」就行。
> **移除过度提示。** 在旧模型上触发不足的工具，现在会正常触发。「如果拿不准就用 X」这类指令会导致过度触发。

### 7. 其他与本项目相关的

| 主题 | 要点 |
|---|---|
| 任务范围 | Opus 5 会自行扩大任务范围；窄任务要显式约束（官方给了一段范文，与本仓 CLAUDE.md 现有段落同源） |
| Subagent | 比前代更愿意委托；小任务上会放大成本，需显式设限 |
| 对话冗长度 | 默认更长，且 **effort 调低不能可靠缩短可见回复**，只能显式要求简洁 |
| 长上下文 | 1M 窗口为默认值，指令遵循在全窗口内保持一致 |
| 长任务 | 若 harness 会自动 compact，应写进提示词，否则模型接近上限时会自行收尾 |

## 二、OpenAI：Codex 官方 harness 的做法

### 1. 删掉「汇报计划/状态」类指令

> 你还应该**移除所有让模型在 rollout 期间沟通前置计划、preamble 或其他状态更新的提示**，因为这会导致模型在 rollout 完成前突然停止。

⚠️ 适用范围：`gpt-5.3-codex` **之前**的版本。5.3 起这些更新变得可提示，并引入了 `phase` 参数（`commentary` / `final_answer`）来防止提前停止——**若 harness 丢掉 assistant 项上的 `phase`，会出现显著性能退化**。

### 2. 官方 starter prompt 的取向

和我们的设计有明显张力：

| Codex 官方 | gro-skills 现状 |
|---|---|
| 「Bias to action：默认带着合理假设实现下去；除非真的被卡住，不要以澄清问题结束回合」 | `build-it`「冲突时停下来」；`interviewing` 追问到共识 |
| 「自主持久：一旦用户给了方向，主动收集上下文、计划、实现、测试、精修，不在每一步等待额外提示」 | 三个控制点要求人工介入 |

这不是谁对谁错——**Codex 优化的是无人值守的长任务，你要的是有控制点的协作**。但意味着在 Codex 上，我们的「停下来确认」需要写得足够具体（什么情况停），否则会与模型的 bias-to-action 打架。

### 3. Review 的处理与我们一致

> 如果用户要求「review」，默认进入代码审查心态……**findings 必须是回复的主体**——摘要和概述要简短且放在枚举问题之后。按严重度排序并给出文件/行引用。若没有发现问题，明确说明，并提及残余风险或测试缺口。

### 4. Plan tool 的纪律

> 简单任务（大约最容易的 25%）跳过计划工具。不要做单步计划。
> **计划收尾**：结束前把每一条先前声明的意图/TODO 对账，标记为 Done / Blocked（附一句理由和一个针对性问题）/ Cancelled。不要留 in_progress 或 pending。

### 5. AGENTS.md 的加载机制

- 从 `~/.codex` 加上仓库根到 CWD 的每一级目录收集
- 按 root-to-leaf 合并，深层覆盖浅层
- **每个文件成为独立的 user-role 消息**，带 `# AGENTS.md instructions for <directory>` 头
- 注入在用户 prompt 之前

### 6. Metaprompting：让模型自己改进指令

官方给了可复用的元提示——在一次表现不佳的回合结束后，让模型读自己的指令并提出针对性增删。建议跑多次取共性，并配 eval 验证。

**这对没有 eval 基础设施的人特别有用**，是我们「攒够五条摩擦再改一次」之外的另一条低成本路径。

## 三、思考伙伴技术：官方文档里的对应物

官方文档没有「苏格拉底式追问」「pre-mortem」这类命名，但有功能等价的落地方式：

| 本地笔记的技术 | 官方文档中的对应 |
|---|---|
| 先问后答、复述+追问 | `<do_not_act_before_instructions>`：意图不明时默认提供信息与建议，而非动手 |
| 攻击判断、找盲点 | 研究场景：「发展多个**相互竞争的假设**，在进度笔记里记录置信度，**定期自我批判**你的方法与计划」 |
| 收束成行动 | Codex 的 Plan closure：每条意图对账为 Done / Blocked / Cancelled |
| 不确定性分级 | 官方无对应，但 `<investigate_before_answering>` 覆盖了「不要臆测未读过的代码」 |

**判断**：思考脚手架的五类模式在官方指南里没有直接对手，属于本地资料的独有价值。它们是**对话技术**，而 gro-skills 是 **agent 指令**——迁移时形态要变（见第五节）。

## 四、反谄媚：无新进展，但风险提示要更新

arxiv 检索 2026 年反谄媚相关工作，未发现比本地笔记（2026-04）更新的实证。检索到的多为 2024–2025 的旧作，唯一 2026 新作是把 Beacon 诊断扩展到印地语（发现文化适配会让谄媚率上升 12–16 个百分点）。

**结论：本地那份笔记仍是最新的，可以直接用。** 但要叠加两条来自官方文档的新约束：

1. **Opus 5 基线已经很低**，而反谄媚 prompt 有实测副作用（Beacon：Gemma 2 27B 准确率 93.33% → 61.33%）。在 skill 里普遍加反谄媚指令，代价可能大于收益。
2. **官方明确说激进措辞会导致过度触发**——本地笔记里推荐的「禁用开场应声」等机制型写法仍然成立（它写的是具体触发模式，不是抽象目标），但要避免升级成 MUST/CRITICAL 语气。

笔记自己的定位也说清了：反谄媚是**协作风格**偏好，应该写 `~/.claude/CLAUDE.md`，不是写进每个 skill。

## 五、写给 agent 的指令 vs 写给对话的 prompt

综合官方文档与社区实践，差异集中在四点：

| 维度 | 对话 prompt | agent 指令（skill / system prompt / AGENTS.md） |
|---|---|---|
| **生命周期** | 一次性，可即时修正 | 常驻，错了会反复生效且难察觉 |
| **篇幅** | 长一点无妨 | 社区经验 50–150 行；**超 300 行合规度下降**，模型开始自行取舍 |
| **形态** | 可以描述期望、给背景 | 命令式、可执行；「用 pnpm，不用 npm」优于「我们倾向 pnpm」 |
| **失败模式** | 答得不好，当场重问 | 静默漂移——你不会知道它没遵守 |

社区侧的补充证据（GitHub 分析 2,500+ 个 `agents.md`）：

> 最好的 agent 文件是通过**迭代**长出来的，不是一次性规划出来的。从简单开始，测试它，**在 agent 犯错时才加细节**。

以及一条与我们 no-op 判据同构的表述：

> **过度填充**：2000 行的 AGENTS.md 会挤占 agent 的工作上下文。把细节移到分包文件或 skill 里。

## 六、对 gro-skills 现状的影响判断

按冲击程度排序。**这一节只做判断，不含改动方案。**

### 🔴 需要重新评估

| 现状 | 冲突点 |
|---|---|
| `prove-it` 作为独立 skill 存在 | 官方说「额外增加验证步骤的遗留 harness 脚手架」应删除。但需区分：**「让它验证」是冗余，「要求它如实报告四态」是输出契约**——后者防的是把「部分验证」说成「通过」，属于官方未覆盖的失败模式 |
| `build-it auto` 内联的验证判据 | 昨天刚加，正撞在「显式验证指令」的枪口上 |
| `review-it`「只报有规格、代码或证据支撑的问题」 | 官方明确说这类限定会让 Opus 5 少报；应改为「全报 + 单独一遍过滤」 |
| `build-it`「交付时说清三件事」 | Codex 上属于 status update 类指令，5.3 之前会导致提前停止；5.3 之后需要 harness 正确处理 `phase` |

### 🟢 已被官方印证

| 现状 | 佐证 |
|---|---|
| 禁令正向化（50 条 → 7 条） | 「告诉 Claude 做什么，而不是不做什么」 |
| no-op 测试删冗余 | 「移除过度提示」「删除而不是重写」 |
| `write-spec` 人区一屏硬线 | 「写入磁盘的文件更长，需要显式长度校准」 |
| 三层结构 + adapter 分层 | 「把细节移到分包文件或 skill 里」 |
| 不用 MUST/CRITICAL 语气 | 「用正常措辞即可，激进措辞导致过度触发」 |

### 🟡 两份本地资料的融入价值

| 资料 | 判断 |
|---|---|
| **思考脚手架**五类模式 | 与 `sharpen-it`（攻击判断）、`interviewing`（澄清问题、探边界）职能重叠但更具体。**收束**（三项收束 / 决策卡片 / 30 分钟行动）是现有 skill 完全没有的一层 |
| **反谄媚**技术 | 机制型写法（第三人称框架、脱身份呈现、给「没问题」的许可、push back 三铁律）可直接用；但**归属应是全局 CLAUDE.md，不是逐个 skill** |

### ⚪ 暂不适用

Metaprompting、compaction 提示、subagent 限流——都是 harness 层能力，不属于 skill 内容。其中 metaprompting 值得单独记一笔，它是无 eval 条件下改进指令的低成本路径。

## 附：可直接复用的官方文本

以下四段来自 Anthropic 官方文档，可按需取用（原文英文）：

**长度校准**
```
Match the length of written documents to what the task needs: cover the substance,
but do not pad with filler sections, redundant summaries, or boilerplate.
```

**范围约束**
```
Deliver what was asked, at the scope intended. Make routine judgment calls yourself,
and check in only when different readings of the request would lead to materially
different work.
```

**Subagent 限流**
```
Delegate to a subagent only for large tasks that are genuinely independent and
parallelizable. Do not delegate work you can finish yourself in a handful of tool
calls, and do not use subagents to verify or double-check your own work.
```

**保守行动（与 bias-to-action 相反的方向）**
```
Do not jump into implementation or change files unless clearly instructed to make
changes. When the user's intent is ambiguous, default to providing information, doing
research, and providing recommendations rather than taking action.
```
